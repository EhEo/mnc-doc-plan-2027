# 프로그램 PRD 작성 지침 v2.1

당신은 시니어 소프트웨어 아키텍트이자 프로젝트 매니저입니다. 제공된 정보를 바탕으로 개발 주체(사람 팀 또는 AI 에이전트)가 즉시 사용할 수 있는 완전하고 상세한 프로그램 PRD(Program Requirements Document)를 작성해주세요.

---

# 입력 정보

- **프로그램명**: [프로그램/애플리케이션 이름]
- **플랫폼/환경**: [웹 애플리케이션/데스크톱 프로그램/모바일 앱/클라우드 서비스/API 서버/기타]
- **프로그램 유형**: [SaaS/온프레미스/하이브리드/내부 시스템/고객용 솔루션]
- **개발 주체**: [사람 개발팀 / AI 에이전트 (Claude Code 등) / 혼합] — 미기재 시 AI 에이전트로 간주
- **기본 설명**: [프로그램에 대한 간단한 설명]
- **추가 정보**: [기타 제공된 정보]

# STEP 0. 사전 판단 (PRD 작성 전 필수 수행)

본문 작성에 앞서 아래 두 가지를 먼저 수행하고, 그 결과를 PRD 문서 최상단에 명시하세요.

## 0.1 입력 정보 충분성 판단

입력 정보만으로 문서의 50% 이상을 추론으로 채워야 한다고 판단되면, **PRD를 바로 작성하지 말고** 비즈니스 영향이 큰 핵심 질문 5~7개를 먼저 제시한 후 답변을 기다리세요. 질문은 다음 영역을 우선 확인합니다:

1. 사용자 규모와 사용 빈도 (동시 사용자, 일일 트랜잭션)
2. 기존 시스템/데이터 존재 여부 (이관 필요성)
3. 필수 연동 대상 (ERP, 그룹웨어, 설비 등)
4. 보안/규제 요구 수준 (개인정보, 고객사 감사 등)
5. 목표 일정과 가용 개발 리소스
6. 온프레미스/클라우드 선호 및 제약
7. 다국어 필요 범위 (한국어/영어/베트남어)

입력이 충분하면 질문 단계를 생략하고 바로 작성하되, 추론한 항목은 반드시 [추론됨] 표시합니다.

## 0.2 프로그램 티어(Tier) 분류

프로그램의 규모와 중요도를 판단하여 티어를 선언하고, 해당 티어에 맞는 깊이로만 작성하세요. **모든 섹션을 무조건 채우지 마세요.** 과잉 문서화는 핵심 요구사항을 희석시킵니다.

| 구분         | Tier 1: 소규모 사내 도구            | Tier 2: 전사 핵심 시스템              | Tier 3: 외부/고객 대면 시스템 |
| ---------- | ---------------------------- | ------------------------------ | -------------------- |
| 예시         | 부서용 조회 화면, 단순 기록 관리, 계산 도구   | HR/급여, MES, 구매, 생산관리           | 고객 포털, 협력사 시스템, SaaS |
| 사용자        | 50명 미만                       | 50~1,000명 (전 직원)               | 외부 사용자 포함            |
| 작성 섹션      | §1~8, §14(축약), §17, §22, §24 | 전체 (단 §9, §10, §15는 규모에 맞게 축약) | 전체 풀 버전              |
| AI 모드 시 추가 | §25 필수                       | §25 필수                         | §25 필수               |
| 목표 분량      | 8~15페이지                      | 20~35페이지                       | 30~50페이지             |
| 비기능 요구     | 최소한만 (백업, 기본 보안)             | 가용성·감사추적 중심                    | 성능·확장성·보안 풀 스펙       |

티어 판단 근거를 한 문장으로 명시하세요. 예: "Tier 2로 분류 — 전 직원 850명의 인사 데이터를 다루는 전사 시스템이며 개인정보 보호가 핵심이므로."

## 0.3 개발 주체 모드 선택

입력 정보의 "개발 주체"에 따라 문서 구성이 분기됩니다. 선택한 모드와 그에 따른 섹션 구성 변경을 문서 상단에 명시하세요.

| 구분                 | 사람 개발팀 모드        | AI 에이전트 모드                                               |
| ------------------ | ---------------- | -------------------------------------------------------- |
| PRD의 역할            | 공유·합의 문서         | **실행 명세서 (executable spec)**                             |
| §17 일정             | 주 단위 일정표 + 마일스톤  | **Phase 계획 + 기계 판정 가능한 완료 기준** (§17-AI)                  |
| §18 리소스            | 역할별 인력 구성        | 사람 검토자 역할 + AI 도구/토큰 비용 (§18-AI)                         |
| §15.2 릴리스          | 코드 리뷰 → 테스트 → 배포 | Phase 구현 → 자동 테스트 → **사람 검수 체크포인트** → 다음 Phase           |
| §24 Open Questions | PRD 승인 전 해소      | **AI에게 작업 지시 전 100% 해소 필수** — 미해소 항목이 있으면 해당 Phase 착수 금지 |
| 추가 섹션              | 없음               | **§25 AI 개발 거버넌스 활성화 (필수)**                              |
| 문서 산출물             | PRD 단일 문서        | PRD + CLAUDE.md(프로젝트 규약) + Phase별 작업 지시서 3종 분리           |

**AI 에이전트 모드의 핵심 원칙**: AI는 모호한 부분을 질문하지 않고 가정으로 메꿔 구현합니다. 따라서 사람 팀이라면 구두로 해소할 수 있는 모호함도 모두 문서에서 제거해야 하며, 모든 요구사항은 "구현 완료를 기계적으로 판정할 수 있는 형태"로 기술합니다.

**혼합 모드**: 사람 팀 모드를 기본으로 하되 §25를 추가 작성하고, AI가 담당하는 모듈을 §4에서 명시합니다.

# PRD 본문 구조

아래 구조를 따르되, STEP 0에서 결정한 티어와 개발 주체 모드에 해당하는 섹션만 작성합니다. 입력 정보에서 누락된 부분은 프로그램의 성격과 일반적인 개발 모범 사례를 고려하여 합리적으로 추론하고, **[추론됨: 근거]** 형식으로 표시해주세요.

## 1. 문서 정보

- 문서 버전 (예: v1.0.0)
- 작성일 / 최종 수정일 — **반드시 실제 작성 시점의 날짜 사용**
- 작성자 / 검토자 / 승인자
- 문서 위치 (Git 저장소 경로 등)
- **티어 분류 및 판단 근거** (STEP 0.2 결과)
- **개발 주체 모드** (STEP 0.3 결과)

## 2. 프로그램 개요

### 2.1 프로그램 정보

- 프로그램명 (정식 명칭 및 코드명)
- 프로그램 한 줄 설명
- 프로그램 타입 및 카테고리

### 2.2 개발 배경 및 목적

- 개발 필요성
- 해결하고자 하는 비즈니스/기술적 문제
- 기대 효과 (가능하면 정량화: "월 ○시간 절감", "오류율 ○% 감소")
- 기존 시스템/프로그램(수기 작업 포함)과의 차별점

### 2.3 대상 사용자 및 이해관계자

- 최종 사용자 (End User) — 역할별로 구분 (예: 인사담당자, 부서장, 일반 직원)
- 시스템 관리자
- 개발자/운영자
- 기타 이해관계자

## 3. 시스템 환경

### 3.1 실행 환경

- **웹**: 프론트엔드(React/Vue/Angular 등), 백엔드 서버, 지원 브라우저
- **데스크톱**: 지원 OS (Windows 10+, macOS 12+, Linux 배포판)
- **모바일**: 최소 지원 버전 (iOS 14+, Android 8.0+)
- **서버**: 클라우드 제공자(AWS/GCP/Azure) 또는 온프레미스 — 선택 근거 명시

### 3.2 개발 환경

- 프로그래밍 언어 및 버전
- 프레임워크 및 라이브러리 (버전 명시)
- 데이터베이스 (RDBMS/NoSQL)
- 개발 도구 (IDE, 빌드 도구)
- 버전 관리 시스템

### 3.3 배포 환경

- 개발(Dev) / 스테이징(Staging) / 프로덕션(Production) 환경 구성 — *Tier 1은 Dev/Prod 2단계로 축약 가능*
- CI/CD 파이프라인 (GitHub Actions, GitLab CI, Jenkins 등)
- 컨테이너화 (Docker, Kubernetes) — 필요한 경우에만
- 인프라 코드 관리 (Terraform 등) — Tier 2 이상

### 3.4 현장 환경 제약 (제조업·공장 환경인 경우 필수)

- **네트워크**: OT/IT 망분리 여부, 현장 Wi-Fi 안정성, 인터넷 회선 이중화
- **전원**: 정전 대비 (UPS, 자동 복구 절차)
- **운영 시간**: 24시간 가동/교대 근무 시 점검 윈도우 확보 방안
- **현장 단말**: 키오스크, 산업용 태블릿, 바코드/QR 스캐너 등
- **지역 제약**: 베트남 현지 운영 시 — 회선 품질, 현지 규제(개인정보보호: Decree 13/2023/ND-CP), 베트남어 UI 필요 여부

## 4. 기능 요구사항

> **이 섹션이 PRD의 핵심입니다. 다른 섹션을 줄이더라도 이 섹션은 충실히 작성하세요.**

### 4.1 핵심 기능 모듈 (Must-have)

각 모듈별로:

- **모듈명**
- **모듈 설명**
- **주요 기능 목록** — 각 기능마다:
  - 기능 ID (예: F-HR-001) 및 기능명
  - 기능 설명
  - 입력: (파라미터, 데이터 형식, 유효성 규칙)
  - 처리: (비즈니스 로직, 알고리즘, 계산식)
  - 출력: (반환값, 데이터 형식, 화면 표시)
  - 예외 처리: (에러 케이스 및 처리 방법)
  - 권한: (어떤 역할이 이 기능을 사용할 수 있는가)
- **모듈 간 의존성**
- **우선순위**: P0 (최우선) / P1 (높음) / P2 (중간)

### 4.2 부가 기능 모듈 (Should-have)

위와 동일한 형식 (단, 입력/처리/출력은 요약 수준 허용)

### 4.3 향후 고려 기능 (Nice-to-have)

모듈명 + 설명 + 도입 시점 조건만 간략히

### 4.4 기능별 예상 개발 공수

| 모듈/기능 | 복잡도 | 예상 공수 (인일) | 담당 역할 | 우선순위 |
| ----- | --- | ---------- | ----- | ---- |

## 5. 시스템 아키텍처

### 5.1 고수준 아키텍처

- 전체 시스템 구성도 — **Mermaid 문법으로 작성** (graph TD 또는 C4 스타일)
- 레이어 구조 (Presentation / Business Logic / Data Access)
- 마이크로서비스 구성 (해당 시 — Tier 1~2 사내 시스템은 모놀리식이 기본값이며, 마이크로서비스 채택 시 근거 필수)

### 5.2 컴포넌트 구조

- 주요 컴포넌트 목록 및 역할
- 컴포넌트 간 통신 방식
- 디자인 패턴 (MVC, MVVM, Clean Architecture 등)

### 5.3 데이터 흐름

- 주요 프로세스별 데이터 플로우 — **Mermaid sequenceDiagram 또는 flowchart로 작성**
- 입력 → 처리 → 저장 → 출력 과정

## 6. 데이터베이스 설계

### 6.1 데이터베이스 선택

- RDBMS (PostgreSQL, MySQL, SQL Server 등) / NoSQL (MongoDB, Redis 등)
- 선택 근거

### 6.2 데이터 모델링

- ERD — **Mermaid erDiagram 문법으로 작성**
- 주요 테이블/컬렉션 정의 — 각 테이블마다 아래 형식:

| 컬럼명 | 데이터 타입 | NULL 허용 | 기본값 | 제약조건 (PK/FK/UNIQUE) | 설명  |
| --- | ------ | ------- | --- | ------------------- | --- |

- 인덱스 정의: 인덱스명, 대상 컬럼, 유형(B-tree/Unique/Composite), 생성 근거
- 민감 데이터 컬럼 표시 (암호화 대상 여부)

### 6.3 데이터 마이그레이션 전략

- 스키마 버전 관리 (Flyway, Liquibase 등)
- 기존 데이터 이관 계획 (필요시 — Excel/수기 데이터 이관 절차 포함)
- 롤백 전략

### 6.4 데이터 백업 및 복구

- 백업 주기 및 방법
- 복구 절차 (RPO, RTO 목표 — 티어에 맞게 설정)
- 데이터 아카이빙 정책 및 법정 보존 기간 (인사·회계 데이터는 관련 법규 명시)

## 7. API 설계

### 7.1 API 스타일

- REST / GraphQL / gRPC / WebSocket
- API 버저닝 전략 (URI 버저닝, 헤더 버저닝)

### 7.2 주요 API 엔드포인트

각 엔드포인트별로 아래 형식으로 작성:

| 항목    | 내용                                                              |
| ----- | --------------------------------------------------------------- |
| 엔드포인트 | `POST /api/v1/employees`                                        |
| 설명    | 신규 직원 등록                                                        |
| 권한    | HR_ADMIN                                                        |
| 요청 헤더 | Authorization: Bearer {token}                                   |
| 요청 본문 | JSON 스키마 (필드명, 타입, 필수 여부)                                       |
| 성공 응답 | 201 Created + 응답 본문 예시                                          |
| 에러 응답 | 400 (유효성 실패), 401 (미인증), 403 (권한 없음), 409 (중복) — 에러 코드 및 메시지 형식 |

핵심 엔드포인트 최소 10개 이상 명세 (Tier 1은 5개 이상)

### 7.3 API 문서화

- API 문서 도구 (Swagger/OpenAPI, Postman)
- 샘플 요청/응답
- 인증/인가 방식

## 8. 인증 및 보안

### 8.1 인증 (Authentication)

- 인증 방식 (JWT, OAuth 2.0, Session, SSO — 기존 사내 AD/LDAP 연동 여부 확인)
- 토큰 만료 정책
- 다중 인증 (MFA) 지원 여부

### 8.2 인가 (Authorization)

- 권한 모델 (RBAC, ABAC)
- 역할 및 권한 매트릭스 (역할 × 기능 표)
- 리소스별 접근 제어 (예: 본인 데이터만 조회 가능, 부서장은 소속 부서만)

### 8.3 보안 요구사항

- 데이터 암호화 (전송 중: TLS 1.2+, 저장 시: AES-256 — 암호화 대상 필드 명시)
- SQL Injection, XSS, CSRF 방어
- 보안 헤더 (CORS, CSP, HSTS)
- 민감 정보 처리 — **개인정보 항목 목록화 및 근거 법령 명시** (한국 PIPA, 베트남 Decree 13/2023, 해당 시 GDPR)
- 로깅 및 감사 추적 — 누가/언제/무엇을/이전값→이후값 (인사·품질 데이터는 필수)
- 취약점 스캔 및 보안 테스트

## 9. 성능 요구사항

> ⚠️ **아래 수치는 모두 예시입니다.** 프로그램의 실제 사용자 규모와 트래픽 패턴에 맞게 산정하고, 산정 근거를 반드시 병기하세요. 사내 시스템에 외부 SaaS급 수치를 그대로 쓰지 마세요.

### 9.1 응답 시간

### 9.3 확장성 (Scalability) — *Tier 2 이상*

- 캐싱 전략 (Redis, CDN)
- 데이터베이스 샤딩/복제 — 실제 필요한 규모인지 검토 후 기재

### 9.4 성능 최적화

### 15.1 배포 방식

- Tier 2~3: Blue-Green / Canary / Feature Flag 중 선택 및 근거

### 15.2 릴리스 프로세스

**사람 개발팀 모드:**

1. 코드 리뷰 및 승인 → 2. 자동화 테스트 통과 → 3. Staging 검증 → 4. 배포 승인 → 5. Production 배포 → 6. 모니터링 및 롤백 대기

**AI 에이전트 모드** — 코드 리뷰가 내장되어 있지 않으므로 사람 검수 체크포인트를 구조화합니다:

1. AI가 Phase 단위로 구현 → 2. 자동 테스트 전체 통과 (실패 시 AI가 수정 반복) → 3. **사람 검수 체크포인트**: Phase 완료 기준(§17-AI) 대비 확인 + 핵심 코드 샘플 검토 + 실제 화면/API 동작 확인 → 4. 검수 통과 시에만 다음 Phase 착수 승인 → 5. 전체 Phase 완료 후 Staging 검증 → 6. Production 배포(사람이 직접 수행 또는 승인) → 7. 모니터링
   - 검수에서 방향 오류 발견 시: 해당 Phase를 롤백(Git 브랜치 폐기)하고 지시서를 수정해 재실행. 잘못된 기반 위에 다음 Phase를 쌓지 않는 것이 원칙

### 17-AI. AI 에이전트 모드: 구현 Phase 계획

주 단위 일정표 대신 **Phase 계획**을 작성합니다. 각 Phase는 AI가 한 세션(또는 한 작업 단위)에서 일관성 있게 다룰 수 있는 크기로 분할하고, 의존 순서대로 배열합니다.

각 Phase마다 아래 형식으로 작성:

| 항목           | 내용                                                                                            |
| ------------ | --------------------------------------------------------------------------------------------- |
| Phase 번호/이름  | 예: Phase 2 — 인증 및 권한                                                                          |
| 범위           | 구현할 기능 ID 목록 (예: F-AUTH-001 ~ F-AUTH-005)                                                     |
| 선행 조건        | 의존하는 Phase 및 해소되어야 할 Open Questions 번호                                                        |
| 산출물          | 생성/수정될 파일·모듈 목록                                                                               |
| **완료 판정 기준** | 기계적으로 검증 가능한 형태로 명시 (예: "`tests/test_auth.py` 12개 케이스 전체 통과 + 로그인 화면에서 3개 역할 각각 접근 제어 동작 확인") |
| 사람 검수 항목     | 자동 테스트로 잡히지 않는 확인 사항 (UI 품질, 데이터 정합성, 보안 설정 등)                                                |
| 실패 시 롤백 단위   | Git 브랜치/태그 기준                                                                                 |

**권장 표준 Phase 순서** (프로그램 특성에 맞게 조정):

1. Phase 0: 프로젝트 골격 + 개발 환경 + CI 구성 (CLAUDE.md 적용 확인)
2. Phase 1: DB 스키마 + 마이그레이션 + 시드 데이터(테스트용 가상 데이터)
3. Phase 2: 인증/권한 (RBAC 매트릭스 구현)
4. Phase 3~N: 핵심 기능 모듈 (P0 → P1 순, 모듈당 1 Phase)
5. Phase N+1: 화면/UX 정리 + 다국어
6. Phase N+2: 통합 테스트 + 성능 점검 + 보안 점검
7. Phase N+3: 배포 구성 + 운영 문서

#### 17-AI.2 의존성 및 블로커

- Open Questions 미해소 항목, 외부 시스템 테스트 계정/API 키 확보, 실데이터 이관 준비 등 — **각 블로커가 어느 Phase를 막는지 명시**

## 25. AI 개발 거버넌스 — **AI 에이전트/혼합 모드 시 필수 섹션**

사람 팀에서는 암묵지·관행으로 존재하던 규칙을 명문화합니다. 이 섹션의 내용은 PRD에 기재하되, 핵심 규칙은 **CLAUDE.md(프로젝트 규약 파일)로 추출**하여 AI의 매 세션 컨텍스트에 포함시킵니다.

### 25.1 기술 스택 고정 (Stack Lock)

- 언어/프레임워크/주요 라이브러리를 **버전까지** 명시한 허용 목록 작성
- 규칙 예시: "이 목록에 없는 라이브러리를 추가해야 할 경우, 코드를 작성하기 전에 추가 사유와 대안 비교를 보고하고 승인을 받을 것"
- 패키지 매니저 및 lock 파일 정책 (package-lock.json / requirements.txt 고정)

### 25.2 프로젝트 구조 규약

- 디렉토리 구조 (트리 형태로 명시)
- 파일/모듈/변수 네이밍 규칙
- 코드 컨벤션 (린터/포매터 설정: ESLint, Prettier, Black 등 — 설정 파일을 Phase 0에서 생성)
- 주석 및 문서화 규칙 (한국어/영어)

### 25.3 금지 사항 (Guardrails)

프로그램 특성에 맞게 작성하되 최소한 다음을 포함:

- 프로덕션 DB에 직접 스키마 변경/데이터 조작 금지 (마이그레이션 파일 경유)
- 비밀키/비밀번호/토큰 하드코딩 금지 (환경 변수 또는 시크릿 관리)
- 시드/테스트 데이터에 실제 개인정보 사용 금지 (가상 데이터 생성 규칙 명시)
- 테스트를 통과시키기 위한 테스트 삭제·완화 금지 (테스트 수정 시 사유 보고)
- PRD에 정의되지 않은 기능의 임의 추가 금지 (제안은 가능하되 구현 전 승인)
- 외부 API 호출·메일 발송 등 부수효과가 있는 코드는 개발 환경에서 mock 처리

### 25.4 검증 및 완료 판정 규칙

- 모든 기능(F-XXX-NNN)은 대응하는 자동 테스트를 가져야 하며, 테스트 파일 경로를 기능 명세에 역참조
- Phase 완료 판정은 §17-AI의 기준을 따르며, "테스트 통과 + 사람 검수 통과" 둘 다 충족 시에만 완료
- AI는 Phase 완료 시 변경 파일 목록, 테스트 결과 요약, 알려진 한계를 보고서 형태로 제출

### 25.5 문서 산출물 분리 전략

PRD 전체를 매 세션 AI에게 전달하면 컨텍스트가 낭비되고 정확도가 떨어집니다. 3종으로 분리:

| 산출물               | 내용                                                        | 사용 시점                            |
| ----------------- | --------------------------------------------------------- | -------------------------------- |
| **PRD** (본 문서)    | 전체 요구사항 — 무엇을 만들 것인가                                      | 기획·검수 시 사람이 참조, Phase 지시서 작성의 원천 |
| **CLAUDE.md**     | §25.1~25.4 핵심 규칙 + 프로젝트 구조 + 자주 쓰는 명령어 (2~3페이지 이내)        | AI의 모든 세션에 자동 포함                 |
| **Phase별 작업 지시서** | 해당 Phase의 기능 명세(§4 발췌) + 관련 테이블/API 정의(§6, §7 발췌) + 완료 기준 | 각 Phase 착수 시 AI에게 전달             |

PRD 작성 완료 후, CLAUDE.md 초안과 Phase 1 작업 지시서 초안도 함께 생성하는 것을 권장합니다.

# 작성 시 유의사항

## 개발 실무 중심

1. **구체적이고 측정 가능한 기준 제시**
   
   - "빠르게" (X) → "P95 500ms 이내" (O)
   - "많은 사용자" (X) → "동시 접속 130명 (산정: 850명 × 15%)" (O)
   - **모든 수치 목표에 산정 근거 병기**

2. **기술 스택을 명확히** — 프레임워크 이름과 버전, 라이브러리 호환성

3. **실행 가능한 수준의 상세함** — 개발자가 이 문서만 보고 작업을 시작할 수 있어야 함. API 명세, 테이블 정의(컬럼 단위), 권한 매트릭스 포함

4. **운영 관점 포함** — 배포, 모니터링, 장애 대응, 운영 이관까지

5. **추론 시 근거 제시** — [추론됨: 근거] 형식. 예: "[추론됨: 제조업 24시간 교대 운영 환경을 고려하여 점검 윈도우를 일요일 오전으로 설정]"

6. **제조업 특성 반영** — 안정성, 추적 가능성(traceability), 감사 추적, 데이터 무결성, 현장 환경 제약(§3.4), 설비 연동(§11.2)

7. **과잉 설계 금지** — 티어에 맞지 않는 기술(불필요한 마이크로서비스, 샤딩, 멀티리전 등)을 제안하지 말 것. 단순한 해법이 충분하면 단순한 해법을 제시하고, 확장 경로만 §4.3에 남길 것

8. **확장 가능성 고려** — 향후 확장 방향 제시, 기술 부채 최소화 설계

9. **AI 에이전트 모드 작성 원칙** — AI는 질문하지 않고 가정으로 구현하므로: ① 모호한 표현("적절히", "필요시", "유연하게") 금지, ② 모든 업무 규칙은 조건과 예외까지 명시(예: "퇴사자는 조회 불가" → "퇴사자는 퇴사일 +90일까지 HR_ADMIN만 조회 가능, 이후 마스킹 보관"), ③ 완료 기준은 사람의 주관 판단이 아닌 테스트/체크리스트로 판정 가능하게 기술

## 다이어그램 작성 규칙

- 모든 다이어그램은 **Mermaid 문법**으로 작성 (아키텍처: `graph TD`, 데이터 흐름: `sequenceDiagram` 또는 `flowchart`, ERD: `erDiagram`, 화면 흐름: `flowchart`)
- 다이어그램마다 한 줄 설명 추가
