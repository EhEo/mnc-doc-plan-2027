# U9C ERP 스키마 분석·문서화 시스템 설계

> 상태: 설계 확정본 (2026-07-24)
> 대상: 用友 U9C ERP (MS SQL Server) 리버스 엔지니어링 및 데이터 사전 자동 생성
> 목적: 미지의 스키마를 데이터 주도로 파악하여, MES·대시보드·추가 시스템이 소비할 "업무별 데이터 맵"과 데이터 사전을 생성

---

## 1. 배경과 문제 정의

- 회사는 用友 U9C(중국 Yonyou ERP)를 MS SQL Server 위에서 운영 중이다.
- U9C는 객체(테이블/뷰/프로시저/함수)가 방대하고, 명명 규약이 직관적이지 않아 **스키마 구조를 알기 어렵다**.
- 트랜잭션마다 코드가 부여되고, 그 코드가 PK/FK 역할을 하며 데이터가 여러 테이블로 흐른다. 관계가 선언된 FK보다 **코드 값 공유**로 이어지는 경우가 많다.
- 수십 명이 동시에 사용하므로 **잠금·세션·검증·임시·로그성 부수 데이터**가 실질 업무 데이터와 대량으로 섞여 있다.
- 따라서 벤더 문서만으로는 부족하고, **입력·이동되는 실제 데이터를 분석해 각 부문이 쓰는 정보를 추정**해야 한다.
- 최종 목표는 MES·대시보드 등에서 쓸 **실질 업무 데이터**(생산실적·입출고·구매·구매요청·비용등록·매출)를 분석으로 식별하고 문서화하는 것이다.

## 2. 목표와 성공 기준

**목표**
- U9C DB의 테이블/뷰/프로시저/함수/관계를 자동 추출한다.
- 실제 사용되는 실질 업무 데이터를 노이즈와 분리해 식별한다.
- 6개 업무 도메인(생산실적·입출고·구매·구매요청·비용등록·매출)의 데이터 맵을 만든다.
- 사람이 읽는 데이터 사전과 기계가 읽는 JSON 맵을 생성한다.
- 결과를 별도 서버의 카탈로그 DB에 누적 저장해 변화도 추적한다.

**성공 기준 (검증 가능)**
- 6개 도메인 각각에 대해 앵커 테이블 → 상세 → 연관 테이블 경로가 근거와 함께 도출된다.
- 각 매핑에 신뢰도와 근거 출처(공개자료 힌트 / QA 델타 확정 / 운영 대조 확인)가 기록된다.
- 데이터 사전(HTML/Excel)과 업무별 JSON 맵이 생성되고, 카탈로그 DB에서 재조회 가능하다.
- 파이프라인이 재실행 가능하며, 재실행 시 신규/삭제/변경 객체 diff가 산출된다.

## 3. 아키텍처 — 3개 존 분리

```
[소스 존: 운영 U9C]        읽기 전용
   │  DMV/Query Store 사용량, 실데이터 프로파일, 스키마 대조 검증, 실사용 XEvents 관찰
   ▼
[분석 존: 분석 PC (Python)]
   │  추출 · 노이즈 분류 · 관계 발견 · 프로파일 · 매핑 · 문서화
   ▼
[카탈로그 존: UAT 서버 신규 DB (ERP_Catalog)]   쓰기
   │  카탈로그 · 매핑 · 스냅샷 · 문서 소스
   ▼
[소비: MES / 대시보드 / 추가 개발]

[실험 존: QA/UAT U9C]      읽기/쓰기 (안전)
      델타 프로빙 · 업무별 XEvents 집중 캡처
```

**이중 환경 역할 분담**
- **운영 U9C (읽기 전용)** — "실제로 무엇이 쓰이는가"의 진실. 사용량 통계, 진짜 데이터 프로파일, 스키마 대조 검증, 실사용 XEvents 수동 관찰. 절대 쓰기 없음.
- **QA/UAT U9C (읽기/쓰기)** — "이 업무가 어떤 테이블을 건드리는가"의 실험장. 델타 프로빙, 업무별 집중 XEvents 캡처.
- **버전 차이 관리** — QA/UAT는 운영과 버전이 일부 다를 수 있다. QA에서 발견한 매핑은 반드시 운영 스키마에 대조(객체·컬럼 존재·타입 일치)한 뒤 확정한다. 한쪽에만 있는 객체는 "버전 차이"로 명시 표기한다.
- **카탈로그 저장소** — 개발용 UAT 서버에 신규 DB `ERP_Catalog`를 생성해 사용한다. 운영·소스와 완전 분리되며, MES/대시보드가 이 DB를 조회한다. UAT 서버가 프로빙 환경과 카탈로그 호스트를 겸할 수 있다.

## 4. 데이터 주도 리버스 엔지니어링 — 3대 기법

스키마가 미지이므로, 구조 추출은 뼈대일 뿐이고 아래 3대 기법이 의미 추정의 중심축이다.

### 기법 1 — 노이즈 필터링 (부수 데이터 걸러내기)

수십 명 동시 사용으로 생기는 잠금·세션·검증·임시·로그성 데이터를 실질 업무 데이터와 분리한다.

- **시스템 컬럼 패턴 탐지** — U9C 공통 감사/조직 컬럼(예: `Org`, `Id`, 생성/수정자·일시, 버전·동시성 컬럼 등)을 자동 식별해 "시스템 컬럼"으로 태깅하고 의미 분석에서 제외한다. (정확한 컬럼명은 §9 지식 베이스 + 실제 스키마로 확정)
- **테이블 유형 분류** — 쓰기만 많고 조회는 거의 없는 테이블, 짧은 수명(생성 후 곧 삭제)·초고회전 테이블, 세션/락/temp 성격 테이블을 "부수(auxiliary)"로 강등한다.
- 결과적으로 "봐야 할 실질 테이블"만 남겨 노이즈를 줄인다.

### 기법 2 — 값 기반 관계 발견 + 트랜잭션 코드 추적

"트랜잭션마다 코드를 부여하고 그 코드가 PK/FK로 데이터가 움직인다"를 정면으로 다룬다.

- 선언된 FK만 믿지 않고, **실제 데이터 값이 공유되는 컬럼 쌍을 발견**해 암묵적(implicit) 관계를 추론한다.
- 문서번호성(코드성) 컬럼을 후보로 식별한 뒤, 같은 코드 값이 여러 테이블에 나타나는 경로를 추적해 **문서 흐름(document flow)을 재구성**한다. (예: 하나의 생산 지시 코드가 헤더→상세→입출고→원가 테이블로 이어지는 경로)
- 이것이 "각 부문에서 어떤 데이터가 어떻게 연결되는지"의 뼈대가 된다.

### 기법 3 — 업무 시나리오 델타 프로빙 (가장 강력)

스키마를 모를 때 가장 확실한 방법이다. 알려진 업무를 1건 수행하고, 그 직전/직후 DB 변화를 포착해 "이 업무 = 이 테이블/컬럼"을 역으로 확정한다.

- 각 업무 도메인별로, 대표 트랜잭션 1건을 QA/UAT에서 수행하기 전후로 테이블별 row 수·max(Id) 스냅샷을 비교한다. **변경된 테이블 = 그 업무가 건드리는 테이블**이다.
- 동시에 **XEvents로 그 순간 실행된 SQL을 캡처**해 어떤 컬럼에 무슨 값이 들어가는지까지 확정한다.
- 두 신호(델타 + 캡처)를 교차 검증하면 추정이 아니라 거의 확정 수준의 매핑이 나온다.
- QA/UAT에서 나온 결과는 운영 스키마에 대조 검증한 뒤 확정한다(버전 차이 관리).

## 5. 처리 파이프라인

| 단계 | 하는 일 | 소스/근거 | 환경 |
|------|---------|-----------|------|
| 1. 구조 추출 | 전체 객체·컬럼·인덱스·선언 FK·의존관계·기존 주석 뼈대 확보 | `sys.*`, `INFORMATION_SCHEMA`, `sys.sql_modules`, `sys.sql_expression_dependencies`, `sys.extended_properties` | 운영(읽기) |
| 2. 노이즈 분류 | 시스템 컬럼/부수 테이블 태깅 → 실질 후보군 축소 | §9 지식 베이스 + 패턴 규칙 | 분석 |
| 3. 사용량 수집 | 테이블별 읽기/쓰기 빈도, 자주 도는 프로시저 Top-N | `sys.dm_db_index_usage_stats`, Query Store, `sys.dm_exec_procedure_stats` | 운영(읽기) |
| 4. 업무 도메인 앵커링 | 6개 목표 업무를 앵커로 설정 | 도메인 정의 + 지식 베이스 힌트 | 분석 |
| 5. 델타 프로빙 + XEvents | 업무별 대표 트랜잭션 수행 → 변경 테이블·컬럼 확정 | 델타 스냅샷 + Extended Events | QA/UAT |
| 6. 값 기반 관계·코드 추적 | 암묵 FK 발견, 문서 코드 흐름 재구성 | 실데이터 값 비교 | 운영(읽기)/분석 |
| 7. 데이터 프로파일링 | 앵커·연관 테이블의 row·최근입력·값분포·코드성 컬럼 파악 | 우선순위 테이블, 대용량은 `TABLESAMPLE` | 운영(읽기) |
| 8. 매핑·의미 부여 | 도메인별 테이블/컬럼에 의미 라벨 + 신뢰도 + 근거 + 수기 보정 | 위 1~7 결합 + 지식 베이스 | 분석 |
| 9. 운영 대조 검증 | QA 발견 매핑을 운영 스키마와 대조(존재·타입), 버전 차이 표기 | 운영 스키마 diff | 운영(읽기) |
| 10. 카탈로그 적재 | ERP_Catalog에 스냅샷 저장(수집일시 기록 → 변화 추적) | catalog 스키마 | UAT DB(쓰기) |
| 11. 산출물 생성 | 데이터 사전(HTML/Excel), 업무별 JSON 맵, ER/의존성 다이어그램 | ERP_Catalog에서 생성 | 분석 |
| 12. 주기 재실행 | 주/월 스케줄 → 스냅샷 누적 → 신규/삭제/변경 diff | — | — |

> ⚠️ DMV 통계는 서버 재시작 시 초기화된다. 그래서 스냅샷을 카탈로그에 누적 저장해 시간축을 확보하는 것이 12단계의 핵심이다.

## 6. 업무 도메인 앵커 (6개)

각 도메인마다 앵커 문서 테이블 → 상세 → 연관 테이블로 확장하고, 3대 기법을 동일하게 적용한다.

1. 생산실적
2. 입출고
3. 구매
4. 구매요청
5. 비용등록
6. 매출

## 7. 카탈로그 스키마 (ERP_Catalog, 별도 SQL Server)

- `catalog.objects` — 모든 객체(테이블/뷰/프로시저/함수) + 유형·스키마·설명·수집일시
- `catalog.columns` — 컬럼 정의(타입·NULL·기본값·PK/FK 여부·시스템컬럼 태그)
- `catalog.dependencies` — 선언 FK + 발견된 암묵 관계 (그래프 원본)
- `catalog.usage_snapshots` — DMV/Query Store 사용량 (수집일시별 누적)
- `catalog.profiles` — 데이터 프로파일 결과(row·최근입력·NULL·distinct·빈도값)
- `catalog.business_map` — 도메인별 매핑. 주요 컬럼:
  - `domain` (생산실적/입출고/구매/구매요청/비용등록/매출)
  - `object_name`, `column_name`
  - `role` (앵커 문서 / 상세 / 연관 / 코드키 등)
  - `confidence` (자동 추정 신뢰도)
  - `evidence` (공개자료 힌트 / QA 델타 확정 / 운영 대조 확인)
  - `verified_by` (사람 보정)
  - `version_note` (운영/QA 버전 차이 표기)

MES/대시보드는 이 스키마를 직접 조회하거나 JSON export를 소비한다.

## 8. 모듈 분해 (독립 테스트 가능 단위)

각 모듈은 표준 dict·DataFrame 인터페이스로 통신하며 개별 실행·검증이 가능하다.

- `extractor` — 구조 추출. 입력: 연결. 출력: raw metadata
- `noise_classifier` — 시스템 컬럼/부수 테이블 태깅
- `usage_collector` — DMV/Query Store 사용량 수집
- `xevents_capture` — Extended Events 세션 관리·파싱 (구버전 Profiler 폴백)
- `delta_prober` — 트랜잭션 전후 스냅샷 비교
- `relation_finder` — 값 기반 암묵 관계·코드 흐름 추적
- `profiler` — 데이터 프로파일링
- `knowledge_base` — U9C 공개 자료 힌트 제공 (§9)
- `mapper` — 점수화·클러스터링·도메인 의미 라벨(신뢰도·근거 포함)
- `reconciler` — QA↔운영 스키마 대조 검증
- `catalog_writer` — ERP_Catalog 적재
- `doc_generator` — HTML/Excel/JSON/Mermaid 생성

## 9. U9C 스키마 규약 지식 베이스 (핵심 요약)

> 원칙: 아래 공개 자료는 매핑 "힌트(가설)"일 뿐이며, 확정은 항상 실제 데이터(델타 프로빙 + 운영 대조)로 한다. 각 매핑의 `evidence`에 근거 출처를 구분해 기록한다.
> 전체 조사 결과·출처·신뢰도·검증 필요 항목은 **`docs/reference/u9c-schema-knowledge-base.md`** 에 있다. 아래는 파이프라인에 직접 쓰는 핵심만 발췌한 것이다.

**아키텍처** — U9C는 SOA·.NET 기반, UAP/UBF 플랫폼(메타데이터 주도), MS SQL Server 표준. enum·업무 의미는 DB가 아니라 UBF 메타데이터에 정의됨 → **정수 코드→의미 매핑은 DB만으로 불가**, 메타데이터/문서 병행 필요.

**테이블 명명 규약** (`모듈접두어_엔티티명`) — 노이즈 분류·도메인 앵커링의 1차 힌트로 사용:

| 접두어 | 모듈 | 6개 도메인 연관 |
|--------|------|----------------|
| `CBO_` / `Base_` | 공공기초객체·마스터 (품목·조직·거래처·창고·BOM 등) | 전 도메인 참조 |
| `PM_` | 구매관리 | 구매 · 구매요청(推定) |
| `PPR_` | 구매가격 | 구매 |
| `SM_` | 판매관리 | 매출 |
| `InvDoc_` | 재고 단거 | 입출고 |
| `IC_` | 재고/원가 | 비용등록(관련) |
| 생산(工单)·재무(GL/AR/AP) | 정확한 접두어 미확인 → 실측 필요 | 생산실적 · 비용등록 |

- 헤더-상세: 헤더 엔티티명 + `Line`/`L` (예: `PM_PurchaseOrder`↔`PM_POLine`), 3단(`...SubLine`)도 존재.
- 다국어는 `_Trl` 접미어 테이블로 분리 → **노이즈 후보**.

**노이즈 필터링용 공통 시스템 컬럼** (기법 1의 핵심 규칙 시드) — 아래 컬럼은 자동으로 "시스템 컬럼"으로 태깅:
`ID`, `Org`, `MasterOrg`, `CreatedBy`, `CreatedOn`, `ModifiedBy`, `ModifiedOn`, `SysMlFlag`, `Effective_IsEffective`(삭제/비활성 플래그), `Effective_EffectiveDate`, `Effective_DisableDate`, `DescFlexField_*`·`KeyFlexField*`(확장 필드).
- ⚠️ 감사 컬럼은 `CreatedBy/CreatedOn` 계열과 `CreateUser/CreateDate` 계열이 **혼재**할 수 있음 → 두 패턴 모두 규칙에 포함.

**PK/FK·문서 흐름** (기법 2의 시드):
- PK는 단일 대리키 `ID`(숫자형, GUID 아님으로 추정 → 타입 실측).
- **헤더-상세 FK 컬럼명 = 부모 엔티티명** (예: `PM_RcvLine.Receivement` → `PM_Receivement.ID`).
- **문서 흐름 추적 핵심**: 상세 행의 `SrcDoc_SrcDocSubLine_EntityID`(원천 단거 참조) + `SrcDocType`(원천 단거 유형) → 단거 계보(주문→출하→입고→매입 등) 재구성의 결정적 단서. 문서번호 `DocNo`, 행번호 `DocLineNo`, 상태 `State`/`Status`.

**실무 권장** — U9C는 DB 갱신이 잦아 정적 사전이 뒤처지므로, UBF의 BE(엔티티) 정의를 "살아있는 사전"으로 병행 참조하는 것이 좋다는 커뮤니티 조언이 반복됨. 본 시스템의 카탈로그가 이 역할을 대체·보완하도록 설계한다.

> §9의 모든 접두어·컬럼·테이블명은 **힌트**이며, 실제 U9C 인스턴스(특히 U9 온프레 vs U9C 클라우드 버전 차이)에서 존재·타입을 실측 검증한 뒤 카탈로그에 확정 반영한다.

## 10. 기술 스택

- Python 3.x + `pyodbc`(ODBC Driver 18 for SQL Server) + `pandas`
- 문서: Jinja2 → HTML, `openpyxl` → Excel (맑은 고딕), 다이어그램은 Mermaid
- 설정: `.env` / `config.yaml` (자격증명 하드코딩 금지), 입출력 `utf-8`
- Extended Events 세션 스크립트(T-SQL) + 결과 파서

## 11. 보안·안전

- 운영 DB는 읽기 전용 계정 사용 (`db_datareader` + `VIEW DEFINITION` + `VIEW SERVER STATE`).
- 운영 서버에는 어떤 쓰기도 하지 않는다.
- 프로파일링은 샘플링·야간 실행으로 부하를 제한한다.
- 델타 프로빙은 QA/UAT에서만 수행한다.
- 자격증명은 하드코딩하지 않는다.

## 12. 단계적 실행 순서

- **Phase 1** — 구조 추출 + 노이즈 분류 + 카탈로그 적재 + 기본 데이터 사전 (가장 빠른 가치)
- **Phase 2** — 사용량 수집 + 우선순위 점수 + 데이터 프로파일링
- **Phase 3** — 델타 프로빙 + XEvents + 값 기반 관계·코드 추적 + 6개 도메인 매핑
- **Phase 4** — 운영 대조 검증 + 대시보드/MES 연동 export + 주기 재실행
